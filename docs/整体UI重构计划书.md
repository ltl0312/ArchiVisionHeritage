### 决策 1 与决策 4 形成的闭环

**首页让位给「营造志」之后，原有的社区信息流并没有被砍掉，而是落到了「匠人社区」这个新入口。** 信息架构因此从"首页既要做自我说明、又要做内容流"的职责挤兑，变成两条清晰的线：

- **营造志（首页）** —— 回答"这个平台是什么、凭什么可信"，承担评审的**第一印象**
- **匠人社区** —— 回答"大家都在做什么"，承担内容沉淀与互动

两侧共用同一套档案卡组件与详情页，不产生重复实现。

## 1. 重构目标与判定标准

**这不是"推翻重做"，而是把「设计稿 ↔ 真实应用」的差距收敛掉。**

| 判定标准 | 量化口径 |
|---|---|
| 设计一致性 | 预览页 **7 个页面**的要素，在真实应用中**逐项存在且视觉等价** |
| 交互可用性 | 每个可点元素都有响应；每个数据界面有 加载 / 空 / 错误 / 无权限 四态 |
| 性能 | 首页滚动 avgFps ≥ 55（在用户实际环境中）、CLS < 0.1、首屏图片总字节 < 1.5 MB |
| 图片体积 | 新上传封面单张 ≤ 400 KB（当前 1.8–4 MB） |
| 令牌完整度 | 视图层硬编码色值 **0 处**（当前 5 文件 / 约 25 处） |
| 移动端 | ≤900px 单列可用、无横向溢出、底部导航可达全部 5 个主入口 |
| 可维护性 | 移动端规则**单一来源**；档案卡等重复结构组件化 |

## 3. 重构的三条不变量

1. **不推翻视觉方向。** 玄墨·金线、三色语义（金=行动 / 青=技术过程 / 丹砂=文化标识）不动。
2. **令牌单一来源。** 所有颜色、间距、圆角、字号只从 `style.css` 的令牌取；组件与视图不得出现字面色值。
3. **过程可见优先。** 冲突时优先保留/增强"能证明技术真实存在"的界面（点云视口、置信度、工序时间轴、状态机），压缩装饰性内容。

## 4. 次级页面设计说明（本轮新增，作为该三页的设计依据）

### 4.1 审核工作台

**取舍：不做数据表格，改"队列 + 侧栏"两区。**
审核是**逐条决策的动作流**，不是**批量比对的数据流**；8 列表格会让"通过/驳回"这两个唯一的动作被淹没在信息里。同时该页在设计稿里本就被定位为"省设计"的对象，重设计必须克制。

- **缩略图必需**：审核对象就是影像，没有图的审核台不可信。
- **驳回强制填理由**，并在提示文案里写明"理由将同步至作者站内信"——把规则**前置在 UI 里**，而不是藏在后端校验中。
- **规则卡常驻在操作旁边**（右侧），减少"忘记标准 → 来回跳转"的损耗。
- **空态明确**："队列已清空 · 全部内容已处理"，而不是留白。
- **最近操作日志**用青色（技术/系统语义），与"待审队列"形成主次。

### 4.2 通知中心

- **四类通知用 V4 三色语义分流**：金 = 数字锦盒（创作成果）、青 = 审核结果（系统）、丹砂 = 互动（社交）。这是三色语义的又一次落地，让用户扫一眼就知道该先处理哪类。
- **未读 → 已读是一等交互**：点条目即已读，另给"全部标记已读"。
- **只有"数字锦盒"带独立行动按钮**（打开锦盒）——因为它是唯一有下游动作的通知类型，其余只需阅读。
- 分类筛选用 **chip 而非 Tab**，与幻筑页的标签语言保持一致。

### 4.3 个人设置

四卡分组：视觉偏好 / 账号资料 / 通知策略 / 关于平台。

- **"视觉偏好"不是装饰**：昼夜流转与全局主题**双向同步**；信息密度**真实改变布局**（`html.density-compact`）。并且把设计理由写进产品文案——"玄墨为默认，为路演投影与三维素材提供最高对比度；宣纸适合长时间阅读文献"。让用户理解为什么默认是深色。
- **"关于平台"承担技术可信度展示**：引擎、渲染管线、后端栈直接列出。评审看到的是可核查事实，不是形容词。
- 所有开关带 `role="switch"` + `aria-checked`。

### P3 · 资源与性能（1 天）—— 决策 3：**不允许改后端**

先说清技术前提：**浏览器无法只解码图片的一部分。** `<img width/height>` 只是布局提示，不会降低解码分辨率；`decoding="async"` 只把解码挪到其他线程。所以"在展示端省内存"这条路走不通，**唯一有效的纯前端手段是在图片进入系统之前把它压小**。

| 编号 | 动作 | 纯前端可行 | 效果 |
|---|---|---|---|
| **P3-A** | `ImageUploader.vue` 增加**上传前 canvas 压缩**：长边 ≤1600px、JPEG q80、按 EXIF 处理方向 | ✅ | 新上传封面 **2–4 MB → ~300 KB**；从源头治理，最有效 |
| **P3-B** | 构建期脚本压缩仓库内静态素材（`generated-images/`、`frontend/public/**`） | ✅ | 随仓库分发的大图一次性瘦身 |
| **P3-C** | **历史已上传封面** | ❌ **无纯前端解法** | 列为**已知残留**：受分页 12 张限制影响可控；若将来允许运维侧介入，可用一次性离线脚本压图（不动业务代码） |
| **P3-D** | 确认 `el-image` 的 `lazy` 滚动容器（D-6）；必要时改用原生 `loading="lazy" decoding="async"` | ✅ | 首屏图片请求分批 |
| **P3-E** | 复核环境光晕 `filter: blur(60px)`，用 Layer borders / Performance 判定；是瓶颈则改 `radial-gradient` | ✅ | 视实测 |
| **P3-F** | `HuanZhuView` 的 `model-viewer` / GLB 按需加载与 `dispose()` 释放 | ✅ | 避免显存随路由累积 |

**门禁**：新上传封面单张 ≤ 400 KB（断言压缩前后字节）；首页图片总字节 < 1.5 MB；Network 面板确认分批请求。
