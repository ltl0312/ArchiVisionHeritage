# V4 · 页面卡顿与头像交互失效 —— 诊断分析与修复计划书

> 状态：**待评审，尚未实施**
> 范围：`frontend/`（Vue 3 应用）与 `frontend/preview/v4-preview.html`（预览页）
> 前置：V4 令牌层已落地（`src/assets/style.css`），默认模式已翻转为玄墨深色

## 0. 结论摘要

| 问题 | 根因（按确定性排序） | 性质 |
|---|---|---|
| **页面卡顿** | ① 卡片封面无固定比例 → 图片加载期反复重排（**确定**）<br>② 大图未做缩略图，按原始分辨率解码（**确定**）<br>③ 多实例 `backdrop-filter`（首页可达 12–36 层）（**高度可疑，需实测**）<br>④ 我在 V4 给 `.glass-card` 新增了 `blur(14px)`（**本次引入的回归**） | 2 项确定 + 2 项待实测 |
| **头像点击无响应** | 分两条路径，**成因完全不同**：<br>· 预览页 → 该控件**从未绑定事件**（设计缺口，非 bug）<br>· 真实应用 → 事件链路正确，但 **V4 把 `--color-surface` 透明度从 35% 降到 4%**，导致弹出菜单「打开了但看不见」（**V4 引入的二阶回归**） | 1 项缺口 + 1 项回归 |

**两条最重要的结论：**

1. 卡顿**不是** Element Plus 全量引入、不是分片配置、不是 Google Fonts 阻塞 —— 这三项项目里已经做对了（见 §1.1）。真正的成本在**图片**与**模糊特效**。
2. 头像问题**大概率不是"事件没绑上"**。`SideNav.vue` 的事件链是正确的；问题在**可见性**。有 10 秒自检法可以立即判定（见 §2.1）。

## 1. 问题一：页面卡顿

### 1.1 已排除的疑点（附证据）

先排除，避免把预算花在错的地方：

| 疑点 | 结论 | 证据 |
|---|---|---|
| Element Plus 全量引入导致卡顿 | **排除** | `main.js` 未调用 `app.use(ElementPlus)`；`vite.config.js` 已配 `unplugin-vue-components` + `ElementPlusResolver` 按需引入 |
| 打包未分片 / 单包过大 | **排除**（仅影响首屏加载，不影响滚动帧率） | `vite.config.js` 已有 `manualChunks`，实际产出 `vendor-vue` / `vendor-element` / `vendor-other` 三包 |
| Google Fonts 阻塞渲染 | **排除** | `index.html` 第 9 行已用 `media="print" onload="this.media='all'"` 异步加载 |
| 瀑布流 JS 动态算行高导致 layout thrashing | **排除** | `CommunityFeedView.vue` 现在是纯 CSS Grid（`repeat(auto-fill,minmax(300px,1fr))`），全项目 grep 无 `getBoundingClientRect` |
| 通知轮询泄漏 | **排除** | `stores/notification.js` 无定时器，仅在 `App.vue` 挂载时取一次未读数 |
| 幻筑页轮询未清理 | **排除**（有次要问题，见 §1.4） | `HuanZhuView.vue:146-151` 有 `onUnmounted` → `clearTimeout(pollTimer)` |
| `body { overflow-x: hidden }`（我 V4 新增） | **不是性能问题** | 该声明会传播到视口，body 本身计算值仍为 `visible`，不产生嵌套滚动容器。仅属代码卫生问题：它会**掩盖横向溢出缺陷**，建议移除后重新验证移动端（见 §1.5 P2-2） |

### 1.2 成因明细

#### 【A】卡片封面无固定比例 —— 确定性缺陷

`PostCard.vue`：

```css
.card-cover-wrap { position: relative; width: 100%; overflow: hidden; }   /* 无 height */
.card-cover-wrap .el-image { width: 100%; display: block; }               /* 无 height / aspect-ratio */
```

```html
<el-image :src="post.preview2dPath" fit="cover" lazy class="card-cover" />
```

`fit="cover"` 只在**容器有确定尺寸**时才有意义；此处容器高度由图片固有比例决定，于是：

- 图片未加载 → 卡片高度 = 0 → 加载完成后高度突增；
- 12 张图陆续解码 → **CSS Grid 行高被反复重算，触发整页 reflow**；
- 叠加 `el-image` 的 `lazy`（IntersectionObserver）→ 滚动过程中持续有新图进入视口，滚动期间不断 reflow → 表现为**滚动掉帧 + 布局跳动（CLS）**。

**这是本问题里唯一可以由代码静态证明的成因。**

#### 【B】大图未做缩略图 —— 确定性缺陷

封面来自后端 `/assets/**`（`WebMvcConfig` 映射本地磁盘，无任何缩放/压缩）。以本次设计使用的素材为例，单张 PNG 为 **1.8–2.3 MB**。

- 卡片实际显示尺寸约 300×200；
- 却要**解码并持有原始分辨率位图**（3200×2400 级别 ≈ 单张 30 MB 显存/内存）；
- 12 张 ≈ 360 MB 位图内存 → 滚动时合成器压力剧增，弱显卡直接掉帧。

这是「首屏 2 秒内很明显、滚动时持续」的典型症状来源。

#### 【C】多实例 `backdrop-filter` —— 高度可疑，必须先实测

`backdrop-filter` 会让每个元素：① 提升为独立合成层；② **每帧对背后内容重新采样并高斯模糊**。

本项目里的分布：

| 位置 | 实例数（首页） | 数值 |
|---|---|---|
| `PostCard.vue` `.card-tag` | **每卡每标签 1 层**（12 卡 ≈ 12–36 层） | `blur(8px)` |
| `CommunityFeedView.vue` `.search-input .el-input__wrapper` | 1 | `blur(8px)` |
| `assets/style.css` `.glass-card` | 视页面而定 | `blur(14px)` ← **我 V4 新增** |
| `ZhiXiView.vue` / `SettingsView.vue` | 各 1，非列表场景 | `blur(10px)` |

→ **`PostCard.vue:193` 的 `.card-tag` 是最大风险点**：滚动列表中的几十个模糊层。

> **为什么要先实测**：`.card-tag` 的 backdrop 是同一卡片内的静态图片，二者相对位置在滚动时不变，浏览器**理论上可以命中缓存**。Chrome 实际是否命中，取决于图层与滚动容器的关系，无法纯静态推断。
> **实测方法**：DevTools → Rendering → 勾选 **Layer borders** 与 **Paint flashing**；再用 Performance 录制 5 秒滚动，看 `Composite Layers` / `Paint` 占比；最后做**对照实验**：临时注入 `* { backdrop-filter: none !important; }`，若帧率显著回升即证实。

#### 【D】大半径固定层模糊（V3 既有，非本次引入）

`assets/style.css` 中 `.ambient-glow-top` / `.ambient-glow-bottom`：`position: fixed` + 400×400 / 300×300 + `filter: blur(60px)`。

- 半径 60px 的模糊需要约为「元素 + 3×半径」的离屏缓冲（≈760×760 × 2 层）；
- 若被提升为合成层且内容不变，滚动成本很低；**若未被提升，则每次绘制都要重新栅格化**，代价极高。
- 判定方法同上：Layer borders 看是否出现独立图层；Performance 看 `Rasterize` 耗时。

#### 【E】次要项

- `transition: all` 出现在 `.nav-btn` / `.nav-icon-box` / `.glass-card` / `.suggest-tag`：`all` 会让浏览器对任意属性变化建立过渡判定，hover 密集时有非零开销。**低优先级**。
- `.feed-card:hover .card-cover { transform: scale(1.03) }`：父级有 `overflow:hidden` + `border-radius`，可能退化为重绘而非纯合成。**低优先级**。

#### 【F】待确认项：`el-image` 的懒加载是否真的生效

Element Plus 的 `lazy` 依赖**滚动容器**判定，默认监听 `window`。本项目真正的滚动容器是 `.main-content { overflow-y: auto }`，**不是 window**。

- 若容器判定错误 → 12 张图在首屏**一次性全部请求并解码**，与【B】叠加，首屏压力翻倍。
- 实测方法：Network 面板按 Disabled cache 刷新 `/home`，观察图片请求是"一次性 12 条"还是"随滚动分批"。

### 1.3 修复方案（性能）

| 编号 | 动作 | 文件 | 预期收益 |
|---|---|---|---|
| **P0-1** | `.card-cover-wrap` 固定比例（建议 `aspect-ratio: 4/3`），并让 `el-image`/`img` 填满容器（`height:100%; object-fit:cover`） | `components/PostCard.vue` | 消除加载期 reflow，CLS → ≈0 |
| **P0-2** | 封面走缩略图：前端请求带尺寸参数，或后端生成 600px 宽缩略图；退路是先在构建期把随仓库分发的素材压到 ≤200 KB | `PostCard.vue` + 后端资源接口（或 `generated-images/` 预处理脚本） | 位图内存降 1–2 个数量级，滚动明显变顺 |
| **P0-3** | **回退我在 V4 给 `.glass-card` 加的 `backdrop-filter: blur(14px)`**（V3 无此项） | `assets/style.css` | 移除本次引入的回归 |
| **P0-4** | `.card-tag` 去掉 `backdrop-filter`，底色不透明度从 `.75` 提到 `.92`（深色）/ `.95`（浅色） | `components/PostCard.vue` | 视觉几乎无差，去掉 12–36 个模糊层 |
| **P1-1** | 首页搜索框去掉 `backdrop-filter`（单实例收益小，但保持一致） | `views/CommunityFeedView.vue` | 小 |
| **P1-2** | 环境光晕改用 `radial-gradient` 预渲染替代 `filter: blur(60px)`（零 filter 成本，观感差异需截图确认）；若坚持保留 blur，则降到 `blur(40px)` 并显式 `will-change: transform` 提升图层 | `assets/style.css` | 视实测结果，可能显著 |
| **P1-3** | 确认并修正 `el-image` 的 `lazy` 滚动容器（必要时传 `scroll-container`，或改用原生 `loading="lazy"` + `decoding="async"`） | `components/PostCard.vue` | 图片请求按需，首屏更轻 |
| **P2-1** | `transition: all` 收敛为显式属性列表 | `style.css` / `SideNav.vue` / `PostCard.vue` | 低 |
| **P2-2** | 移除 `body { overflow-x: hidden }`（我的 V4 新增），改由 `.app-root` 承担裁切，并**在 390px 复测横向溢出** | `assets/style.css` | 消除"掩盖缺陷"的隐患 |

### 1.4 顺带发现（同批修复）

`views/HuanZhuView.vue:115-144` —— `pollTaskStatus()` 每次调用都会新起一条 `setTimeout` 链，但**不会清理上一条**。用户在结果返回前重复点击「生成三维幻境」会并发多条轮询链，各自持续请求 `/tasks/{id}/status`。

建议：`pollTaskStatus` 入口处先 `clearTimeout(pollTimer)`，并加一个"已有任务进行中则直接 return"的守卫。

### 1.5 修复顺序建议

```
第 1 步（measure）：按 §3.2 采集基线（FPS / CLS / 图层数 / 图片请求时序）
第 2 步（P0-1、P0-3、P0-4）：零风险、纯收益，先落
第 3 步（复测）：确认 FPS 是否达标；若未达标再执行第 4 步
第 4 步（P1-2、P1-3、P0-2）：需要实测数据支撑的项
第 5 步（P1-1、P2-1、P2-2、1.4）：清理项
每步独立提交，便于逐项回滚与归因
```

## 2. 问题二：点击头像无响应

### 2.1 先做 10 秒自检（判定你测的是哪个界面）

| 观察 | 判定 |
|---|---|
| 地址栏是 `.../static-html/.../v4-preview.html` 或 `file://.../v4-preview.html` | → **情形 A：预览页** |
| 地址栏是 `localhost:5173` / `4178` 等应用端口 | → **情形 B：真实应用** |
| 点击后**头像变半透明** | → 情形 B，且**事件是通的**，问题在"菜单看不见" |
| 鼠标在侧栏下半部导航区缓慢扫过，有极淡文字块浮现 | → 情形 B，证实"菜单打开了但不可见" |

### 2.2 情形 A：预览页（`frontend/preview/v4-preview.html`）

**根因：该控件从未绑定任何事件，是设计缺口，不是 bug。**

- 侧栏用户条 `.me`（梁思成 · 研究员）与顶栏 `.avatar.lg` 都是纯展示 `<span>`；
- 预览页的定位是"看视觉"，我在交付时只实现了导航、上传/解析、营造工序、状态机、主题切换五组交互，**用户菜单没有做**。

**修复**：在预览页补一个与真实应用等价的用户弹出菜单（条目：个人信息 / 设置 / 通知中心 / 昼夜流转 / 管理控制台 / 安全退出），并在「检查控制台」增加 `用户菜单：开 / 关` 项，便于你直接检查定位、间距、动效与明暗对比。

### 2.3 情形 B：真实应用

**根因：事件链路是正确的，问题出在「可见性」。**

`components/Layout/SideNav.vue` 的事件链复核：

```js
// 触发区（第 80 行）
<div class="user-trigger" @click="menuOpen = !menuOpen" :class="{ active: menuOpen }">

// 外部点击关闭（第 137-148 行）
function onDocClick(e) {
  if (menuRef.value && !menuRef.value.contains(e.target)) menuOpen.value = false
}
document.addEventListener('mousedown', onDocClick)
```

- `menuRef` 挂在 `.sidebar-footer`（第 34 行）上，而 `.user-trigger` 正是它的子节点 → `mousedown` 判定为"内部"，**不会**抢先关闭；
- `mousedown` → `click` 的顺序正确，`menuOpen` 会正常翻转；
- 未发现 `pointer-events`、`z-index`（`.sidebar` 20 > `.main-content` 10）、`overflow` 遮挡问题；
- `BrocadeDialog` 是 `el-dialog`，关闭态不产生全屏遮罩。

→ **事件是通的。** 那么"没反应"只能来自渲染：

**V4 引入的关键变量变化：**

| Token | V3 深色 | V4 深色 | 影响 |
|---|---|---|---|
| `--color-surface` | `rgba(41, 37, 36, 0.35)` | `rgba(255, 255, 255, 0.04)` | **用作"表面底色"时几乎完全透明** |

而 `.user-menu` 的样式是：

```css
.user-menu {
  background: var(--color-surface);      /* → 4% 白 */
  border: 1px solid var(--color-border); /* → rgba(255,255,255,.08) */
  box-shadow: var(--shadow-modal);       /* → 黑色投影 */
}
```

逐层 alpha 合成（`4% 白` 叠在 `4% 白` 的侧栏上，再叠在 `#0A0A0C` 上）：

```
菜单区域最终色 ≈ rgb(19,19,22)
侧栏背景最终色 ≈ rgb(15,15,18)
对比度 ≈ 1.03 : 1
```

**结论：菜单确实会弹出，但它与背景的对比度约 1.03:1，肉眼不可分辨；投影是黑色压在近黑底上，同样不可见。** 用户看到的只是几行文字浮在导航项上方，因此判断为"点了没反应"。

**同一根因的连带问题**：`.sidebar { background: var(--color-surface) }` 也变成 4% 白 → **侧栏与主内容区之间失去分界**，V4 深色下整个应用呈现"一片黑"，层级关系丢失。这是 V4 令牌层的系统性缺陷，不止影响用户菜单。

**修复方案：**

1. **补齐"浮层"语义 token**：在 V4 令牌中新增 `--color-surface-float`（深色取 `#191720` 或 `#1E1B24`，浅色取 `#FFFFFF`），并把所有**真正需要浮起**的组件改用它：
   - `SideNav.vue` → `.user-menu`
   - `style.css` → `--el-bg-color-overlay`、`--el-bg-color`、`.el-dropdown-menu` / `.el-popover` / `.el-dialog` 覆盖段（多数已指向 `--color-surface-solid`，需核对一致性）
2. **恢复侧栏层级**：`.sidebar` 底色改用 `--color-bg-elev`（`#111014`），而不是 `--color-surface`；
3. **复核 `--color-surface` 的取值**：4% 作为"卡片"偏弱，建议提到 `5.5%–6%`（需整体视觉回归，因为 9 个视图都依赖它）；
4. **可访问性补强**：`.user-trigger` 增加 `aria-haspopup="menu"` / `aria-expanded`，`Esc` 关闭；`.user-menu` 增加 `role="menu"`。

> 若自检结果与上述不符（例如点击后头像**没有**变半透明，且侧栏扫不出任何文字块），则说明存在第二个未观测到的遮挡层。此时按 §3.2 的方法先抓 DOM 快照与 `elementFromPoint()` 命中结果，再做结论。

## 4. 验证方式

### 4.1 量化指标（先采基线，修复后对比）

| 指标 | 采集方式 | 目标 |
|---|---|---|
| 滚动帧率 / 掉帧率 | 无头 Chrome 注入 `requestAnimationFrame` 计数，程序化滚动 3 秒，统计 >16.7ms 的帧占比 | 掉帧率 < 10%（基线先测，再定阈值） |
| 合成层数量 | DevTools → Rendering → **Layer borders** 截图 + `Layer` 计数 | 首页模糊层数从 12–36 降到 ≤2 |
| 重绘 / 光栅化耗时 | Performance 录制 5s 滚动，统计 `Recalculate Style` / `Layout` / `Rasterize` 总时长 | Layout 总时长下降 ≥ 50% |
| 布局偏移 CLS | `PerformanceObserver` 监听 `layout-shift`，程序化滚动采集 | CLS < 0.1（当前预计 > 0.3） |

## 5. 潜在风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 给 `.card-cover-wrap` 加 `aspect-ratio` 会改变首页卡片外观（高度可能变化） | 视觉回归，用户可感知 | 先截图对比 4:3 / 3:2 / 16:10 三种比例再定；单独提交便于回滚 |
| 移除 `backdrop-filter` 会轻微改变卡片标签质感 | 视觉降级，幅度小 | 用提高不透明度补偿；截图对照 |
| 调整 `--color-surface` 取值会影响**所有** 9 个视图 | 面较广，可能连带出现对比度不当 | 独立提交、独立回滚；逐视图截图核对 |
| 光晕改 `radial-gradient` 后观感差异 | 氛围感变化 | 截图对比；若不满意则退回 `blur(40px)` + `will-change` |
| 移除 `body{overflow-x:hidden}` 后移动端可能出现横向溢出 | 移动端可用性 | 必须在 390px 复测；若溢出则修根因而非重新隐藏 |
| 封面缩略图若引入后端改动 | 触碰后端，扩大范围 | 列为 P0-2 的"完整方案"，在性能数据确认必要性后再做；先用前端侧压缩兜底 |
| 头像问题若实测并非"可见性"而是存在第二遮挡层 | 修复方案失效 | §3.2 的 DOM / `elementFromPoint` 取证先行；本计划书按"事件正确 + 可见性缺陷"为前提，该前提已在 §2.1 给出 10 秒自检 |

**回滚策略**：所有改动按 §1.5 分 5 步独立提交，每步可单独 `git revert`。`.glass-card` 的 `backdrop-filter` 回退与 `--color-surface` 复核属最高优先级、最低风险，即使后续步骤全部搁置也应先落。
